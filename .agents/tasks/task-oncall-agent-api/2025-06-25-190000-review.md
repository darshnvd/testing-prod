# OnCall AI Agent Control Plane API

An Express REST API implementing an AI-powered on-call agent's control plane: agent lifecycle, incident triage with mock AI diagnosis, runbook execution with approval gates, escalation policies, knowledge base search, notification dispatch, and observability queries. The entire system operates against in-memory data stores seeded with realistic mock data; no external dependencies are required to run or test. Authentication is a single shared Bearer token compared against an env var (or a hardcoded default).

**Watch for:** Hardcoded default API key shipped in source (confirmed). Shared mutable state across requests with no isolation between tests (confirmed). Unbounded config mutation with no schema validation (confirmed). Escalation actions are fire-and-forget with no persistence (confirmed).

## High-level view

Authentication is a static token comparison with a hardcoded fallback baked into the source. A production deployment that omits the `API_KEY` env var silently accepts a credential that appears in the README and `.env.example`.

The data layer is a single module exporting mutable arrays and objects. Tests share this state across the entire suite without reset, creating ordering dependencies. The agent lifecycle tests must run stop-then-start in sequence, and any test that creates incidents, executions, or documents permanently mutates the shared store for subsequent tests.

Runbook execution implements a two-phase approval gate, but the escalation trigger endpoint (`POST /escalation-policies/escalate`) constructs an escalation object with notified targets, never persists it, and never dispatches notifications. The endpoint returns data implying action was taken while performing none.

The observability routes generate synthetic metrics and logs on every request. Responses contain no field indicating data is simulated, which could mislead consumers integrating against this API expecting real telemetry.

<summary>Issues (7)</summary>

1. **Hardcoded default API key** — `src/middleware/auth.js` falls back to `oncall-agent-secret-key-2024` when `API_KEY` env var is unset. Remove the fallback and fail fast on startup if the env var is missing.
2. **Fragile auth exemption** — The health-check bypass is a hardcoded string comparison (`req.path === '/api/v1/agent/health'`). Any refactoring of mount paths will silently break it. Extract the skip-list to configuration or apply auth selectively to route groups.
3. **Shared mutable state in tests** — Tests depend on execution order (stop before start). Use `beforeEach` to reset state or isolate test groups to avoid cascading failures when running with `--randomize`.
4. **Escalation has no side effects** — `POST /escalation-policies/escalate` returns an escalation object but doesn't persist it or trigger notifications. Persist to an `escalations` array so consumers can query past escalations.
5. **No input sanitization on config merge** — `PATCH /agent/config` does `Object.assign(agentState.config, updates)` with whatever the client sends. An attacker with a valid token can inject arbitrary keys or overwrite `notificationChannels` with a non-array type. Add a whitelist of allowed config keys.
6. **Agent state not reset on stop** — `POST /agent/stop` sets status to "stopped" but doesn't clear `startedAt`, so `GET /agent/status` computes a growing uptime from a stale timestamp for a stopped agent.
7. **No rate limiting** — The API has no rate limiting middleware despite exposing destructive operations (start/stop, resolve incidents, execute runbooks) behind a single shared token.

## Hardcoded credential in auth middleware

The authentication middleware (`src/middleware/auth.js:23`) resolves the API key as:

```javascript
const apiKey = process.env.API_KEY || 'oncall-agent-secret-key-2024';
```

A production deployment that forgets to set `API_KEY` silently falls back to a credential committed to source control and documented in the README. The `.env.example` file also contains this value. The mitigation is to fail on startup if the env var is absent, not to provide a default.

## Unbounded config mutation

`PATCH /api/v1/agent/config` validates only that the body is non-empty, then merges it directly:

```javascript
Object.assign(agentState.config, updates);
```

A request body like `{"notificationChannels": "not-an-array", "injectedKey": true}` corrupts the config shape with no schema enforcement. Any downstream code expecting `notificationChannels` to be iterable would fail with an opaque runtime error.

## Escalation is ephemeral

`POST /escalation-policies/escalate` builds an escalation response object with `notifiedTargets` but never writes it anywhere. No `escalations` array exists in the store, and no notification is dispatched. The endpoint returns a 200 with data that implies action was taken, but nothing was persisted. A consumer has no way to query past escalations or verify that notifications were sent.

## Agent lifecycle state inconsistency

When the agent is stopped via `POST /agent/stop`, the handler sets `agentState.status = 'stopped'` but leaves `agentState.startedAt` unchanged. The status endpoint then computes uptime from that stale timestamp:

```javascript
const uptimeMs = agentState.startedAt
  ? Date.now() - new Date(agentState.startedAt).getTime()
  : 0;
```

A stopped agent reports a continuously growing uptime.

## Test coupling and missing coverage

The test suite shares a single app instance backed by mutable singleton state. The agent lifecycle tests stop the agent then start it, relying on that specific order to trigger the 409 conflict on duplicate start. Running with `jest --randomize` would produce failures.

Not tested: error handler middleware invocation (no test triggers an uncaught exception), `POST /agent/stop` when already stopped (409 case), deployment filtering by `since` parameter, log query filtering by `query` string, knowledge base search with `service` and `tags` filters combined, and the root `/` endpoint response shape.
